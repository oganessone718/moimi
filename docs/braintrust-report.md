## 1. 합의점 (Consensus) — 4개 AI 전원 동의, Confidence H

### C1. MVP 범위 과대 — F6(중간지점)·F7(시간대)·F8(타임존)을 v1.1로 후퇴하라
- **전원 동의(H)**. 1인 포폴에 9개 기능(S0~S9)은 과적재.
- **F8 타임존**: "한국 사용자 대상"(Plan §2)이라 명시하고 F8/데이터모델에 UTC 변환을 넣은 것은 **내부 모순**(Gemini, Kimi가 가장 강하게 지적). UTC 저장 원칙만 초기 반영하고 변환 UI는 제거.
- **F7 시간대**: 날짜+시간+장소 = 사실상 3차원 투표 매트릭스 → 모바일에서 UX 복잡도 폭증. When2meet 스타일 히트맵은 그 자체로 별개 프로젝트 규모.
- **F6 중간지점**: 단순 centroid는 바다/산을 가리킬 수 있고, "현실적 중간지점"은 대중교통 가중치(길찾기 API)가 필요. 출발지 입력은 전환율을 해치는 허들 — Plan도 §9에서 인정하면서 MVP에 포함한 모순.
- **권장 v1 코어**: F1(장소+날짜 동시조율) + F2(무가입 게스트) + F4(카톡 공유) + F5(지도 마커) + F9(반응형). → S0~S5로 축소, 구현량 약 40% 감소, 1인 4~6주 현실화.

### C2. Drizzle "RLS 친화" 근거는 과장 — ORM 선택과 RLS는 직교
- **전원 동의(H/M)**. RLS는 **DB 레벨 정책**이므로 ORM이 해결하지 않는다. Drizzle이든 Prisma든 `set_config()`/커스텀 JWT로 RLS 컨텍스트를 raw SQL 주입해야 함.
- Drizzle의 **진짜 장점**: Edge/Serverless 친화 + SQL 가시성 + 포폴 신선도. "RLS 친화"는 근거에서 빼라.
- Kimi는 **Prisma가 1인 포폴에 오히려 나을 수 있다**고 지적(마이그레이션 성숙도, AI 도구의 Prisma 스키마 작성 능력). 단, Drizzle 채택 자체는 합리적이라는 데는 전원 동의.

### C3. 4자리 PIN + 단일 shareToken + localStorage 모델의 보안 허점
- **전원 동의(H)**. 핵심 취약점:
  1. **PIN 무차별 대입**: 4자리 = 10,000 조합. Plan은 "rate limit" 언급만 있고 구체 메커니즘(최대 시도 후 잠금, IP+token 복합키, 지수 백오프) 부재. IP 기반만으론 VPN/프록시 우회.
  2. **shareToken 유출 = 모임 전체 노출**: 단톡방 공유 시 의도치 않은 인원 접근/오염. 만료/취소 메커니즘 없음. URL 토큰은 Referer·히스토리·OG 크롤러에 노출.
  3. **"PIN 검증 후 권한 부여" 상태 유지 방식 미정의**: 쿠키 세션? 서명 JWT? admin_sessions 테이블? — 이게 없으면 "PIN 한 번 맞히면 영구 관리자" 또는 CSRF 세션 탈취 위험.
  4. **게스트 사칭**: 시크릿 모드 → 새 guestKey → 다중 투표. 본질적으로 무가입 모델 한계이나 명시 필요.

### C4. 카카오 인앱 브라우저 리스크가 통째로 누락됨 (가장 치명적인 숨은 함정)
- **전원 동의(H)**. 트래픽 대부분이 카톡 인앱 브라우저인데 Plan에 대응책 전무.
  - localStorage가 인앱 ↔ 외부 브라우저 간 분리/휘발 → guestKey 지속성 깨짐 → 응답 수정 불가 → 4자리 PIN 의존도만 상승.
  - 카카오 로그인(S9) 시 팝업 차단/리다이렉트 루프 가능성.
  - 좁은 뷰포트·제한 메모리에서 F1·F5 복잡 렌더링 검증 안 됨.

### C5. 부록 A "미확인 항목"이 곧 아키텍처 블로커 — S0/S1 이전 PoC 필수
- **전원 동의(H)**. Supabase Auth ↔ 카카오 OAuth 공식 지원 범위, Kakao Share 템플릿 승인, RLS+PIN 컨텍스트 주입 방식이 모두 미확인인데 핵심 의존성. 하나라도 실패 시 전면 재설계 또는 바이럴 핵심 불가. Plan의 S0 검증기준("빈 앱 배포 성공")은 너무 약함.

## 2. 분기점 (Divergence)

### D1. Supabase RLS를 쓸 것인가, 폐기할 것인가
| AI | 입장 | 근거 |
|----|------|------|
| **Gemini** | **RLS 폐기**(가장 강경) | 무가입이 기본인데 게스트에게 억지 anon 세션 발급해 RLS 통과시키는 건 오버엔지니어링. 어차피 Server Action에서 토큰/PIN 검증할 거면 RLS 불필요. Server Actions + Drizzle 비즈니스 로직으로 접근제어 단순화 |
| **OpenAI** | **RLS 유지하되 고위험 인지** | 토큰 기반 RLS는 "정책 1개 누락 = 전체 유출"의 고위험 영역. 쓰되 테이블별 접근 테스트를 S1 완료조건으로 강제 |
| **Claude** | **RLS 유지 + PoC 선행** | Supabase가 요구사항에 최적합. 단 shareToken을 RLS 컨텍스트에 주입하는 메커니즘 PoC가 S1 최대 블로커 |
| **Kimi** | **RLS 유지(중립)** | anon 키 + 토큰 기반 RLS로 어느 정도 방어 가능. 단 복잡성 증가 인정 |

→ **의장 판단**: 포폴 어필(실서비스형 RLS 설계 시연) vs 단순성·완성 확률의 트레이드오프. **무가입 게스트 경로는 Gemini 안(서버 액션 검증)으로 단순화**하고, **로그인 사용자 대시보드에만 RLS를 제한적으로 적용**하는 절충이 가장 합리적. 게스트 데이터에 RLS를 억지로 쓰지 말 것.

### D2. ORM 최종 선택 (Drizzle 유지 vs Prisma 회귀)
- OpenAI·Claude·Gemini: **Drizzle 유지** 무방(신선도·Edge·SQL 가시성).
- Kimi: **Prisma 재고** 가치 있음(생태계 성숙, AI 코드 생성 친화).
- → **의장 판단**: 포폴 신선도 목적이면 Drizzle 유지. 단 "RLS 친화"가 아니라 "Edge+SQL 가시성+모던"을 근거로 재기술. 복잡 쿼리(집계/추천)에 raw SQL 병용 준비.

### D3. 시장 차별점의 유효성 (니치 vs 함정)
| AI | Confidence | 뉘앙스 |
|----|-----------|--------|
| **OpenAI** | M | 니치 존재. 단 30초 내 투표 완료로 마찰 제거해야 현실화 |
| **Claude** | M | 초기 프로토타입 실사용으로 검증된 플로우라는 강점. 단 강자가 피한 4가지 이유(UX 복잡도/캘린더 API/수익화/저빈도) 미반박 |
| **Gemini** | M(가장 비관) | "틈새가 아니라 인지부하로 의도적 회피한 영역". 멘탈모델은 "시간 확정 후 장소". n×m 변수 = 이탈 직결 |
| **Kimi** | M | 공백은 실재하나 PMF 미검증. 출시 전 지인 수동 테스트로 가설 검증 권장 |

→ 전원 Confidence M. **차별점은 존재하나 그 니치의 크기·UX 해결 가능성은 미검증**이라는 데 수렴. 포폴 목적이므로 PMF 자체는 부차적이나, "왜 강자가 안 했나"에 대한 답(예: 한국 카톡 문화 특화)을 데모에 녹여야 설득력.

## 3. 종합 분석 (의장)

이 Plan은 **개념적으로 견고하고 자기인식(self-awareness)이 높다** — 부록 A에서 미확인 항목을 솔직히 명시하고, §9에서 범위 후퇴 가능성을 열어둔 점은 우수하다. 그러나 **4개 AI가 만장일치로 지적한 두 축의 결함**이 있다.

**축 1 — 범위의 비현실성**: "한국 타겟"이라면서 타임존(F8)을, "전환율 최대화"라면서 출발지 입력(F6)을, "When2meet 단순성 계승"이라면서 시간 매트릭스(F7)를 동시에 넣었다. 세 기능이 서로의 전제와 모순된다. 1인 포폴은 "완성되지 않은 큰 것"보다 "완성된 작은 것"이어야 한다(Kimi).

**축 2 — 인증/보안 모델의 미완성**: 무가입 트레이드오프 자체는 업계 공통(When2meet)이라 수용 가능하나, Plan은 **"PIN 검증 후 권한을 어떻게 유지하는가"**와 **"카톡 인앱 브라우저에서 localStorage가 살아남는가"**라는 두 핵심 질문에 답하지 않았다. 이 둘은 S1 데이터모델보다 먼저 PoC로 풀어야 할 선행 과제다.

긍정 신호: 스택 선택(Supabase+Kakao)은 전원이 한국 B2C·1인 개발에 적합하다고 평가. 핵심 차별점(장소+날짜+카톡)의 데모 임팩트는 충분.

## 4. Plan 수정 권고 Top 5 (우선순위)

### ⭐ P0. MVP 범위를 6개로 축소 — F6/F7/F8을 v1.1로 후퇴, F3은 S9 유지
- v1 코어: **F1·F2·F4·F5·F9** (S0~S5). F8 타임존은 즉시 제거(UTC 저장 원칙만 유지). F6·F7은 v1.1.
- 근거: 4개 AI 만장일치(H). 구현량 ~40% 감소, 1인 4~6주 현실화.
- 효과: "한국 타겟 vs 타임존" / "전환율 vs 출발지 입력" 내부 모순 동시 해소.

### ⭐ P1. S0 이전 "카카오 3종 + Supabase Auth 연동 + 인앱 브라우저" PoC를 0순위로
- 부록 A 미확인 3항이 모두 카카오 관련이며 바이럴 핵심. S0 검증기준을 "빈 앱 배포"에서 "카카오 로그인/맵/공유가 카톡 인앱 브라우저에서 동작"으로 격상.
- 실패 시 폴백 명시: Auth.js 카카오 provider → 최악엔 구글만.

### ⭐ P2. 인증 권한 모델을 재정의 — 게스트는 서버 액션 검증, RLS는 로그인 대시보드로 한정
- shareToken 게스트 경로에 억지 RLS 적용을 폐기(Gemini)하고, Next.js Server Action에서 토큰/PIN 검증으로 단순화.
- 관리자 인증 상태는 **짧은 TTL(예: 30분) httpOnly 서명 쿠키**로 부여, 영구 권한·매요청 PIN 재전송 둘 다 회피. CSRF 방어 필수.
- RLS는 로그인 사용자의 "내 모임 대시보드"에만 제한 적용 → 포폴 시연 가치는 유지하면서 게스트 경로 위험 제거.

### ⭐ P3. PIN·토큰 보안 가드레일을 S1 완료조건 체크리스트로 강제
- 관리자 PIN **6자리 이상**(4자리는 해시해도 사실상 평문 수준 — Kimi).
- PIN 실패: 5회 잠금 + 지수 백오프 + IP+shareToken 복합 rate limit + CAPTCHA 트리거.
- shareToken **최소 128bit(22자 base62)**, `Referrer-Policy: no-referrer`.
- 데이터 만료: 무가입 생성 스팸 대비 Meeting TTL(예: 90일 비활동 삭제) — 무료 티어 500MB 보호.
- 테이블별 RLS 접근 테스트(특히 조인 테이블 DateVote/PlaceVote/Comment)를 S1 통과 조건에.

### ⭐ P4. 게스트 식별을 localStorage 단독에서 탈피 — 응답 수정 매직링크 도입
- 카톡 인앱 브라우저 localStorage 휘발/분리 문제로 guestKey 신뢰 불가.
- 대안: 응답 제출 시 **개인용 수정 링크(edit-link, 서명 토큰)**를 발급해 화면/카톡으로 제공(PIN보다 UX·보안 우수 — OpenAI). guestKey는 best-effort 자동인식 보조로만.
- (선택) 로그인 merge 로직의 엣지케이스(다기기 중복 참여, 기 연결 guestKey, 공유 기기)를 S9 설계 시 명시 — Plan의 "자동 연결" 한 줄은 위험.
